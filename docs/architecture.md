# Architecture

Nimbus begins with seven Node.js processes behind real HTTP boundaries. The gateway validates identity and sends orders to the orchestrator. The orchestrator reserves inventory synchronously, then dispatches an `order.created` event to three consumers asynchronously.

Every outbound call reports its measured status and duration to the control plane. The topology engine aggregates those observations into queryable dependency edges; it does not use hard-coded edges. Edges expire five minutes after their latest observation so graph, path, and incident blast-radius reads represent current traffic. A later observation starts a fresh aggregate instead of mixing expired measurements into the live edge.

```text
gateway -> identity-api
gateway -> order-orchestrator -> inventory-api
                           \-> PostgreSQL outbox -> RabbitMQ -> payment-worker
                                                              -> notification-router
                                                              -> analytics-ingestor
services -> OpenTelemetry Collector -> Jaeger
```

Order creation and its `order.created` envelope commit together in PostgreSQL. A background publisher atomically claims pending outbox rows and publishes persistent messages to RabbitMQ using publisher confirms; only a broker confirmation marks the outbox row published. Three durable quorum queues retain independent consumer work through broker and consumer restarts. Each consumer records its event ID in PostgreSQL before running its current side effect, then acknowledges the broker message, so redelivery remains idempotent. Delivery is at-least-once, not exactly-once. See [event delivery](event-delivery.md) for retry, dead-letter, and recovery operations.

Each service emits HTTP and RabbitMQ spans through a health-checked local OpenTelemetry Collector to Jaeger. W3C trace context follows HTTP headers, is stored with the transactional outbox event, and resumes when the event is published after an orchestrator or broker outage. Correlation and idempotency IDs are span attributes; request bodies and credentials are not captured. This tracing extends the existing measured topology rather than replacing it. See [local tracing](tracing.md) for inspection and retention details.

The production API uses the standards-compliant `graphql` package. `POST /graphql` currently exposes the service catalog, observed graph, and BFS shortest paths.

The operations engine retains up to the latest 100 measured outbound calls per service within a five-minute live-data horizon. A quiet service becomes unknown after its samples expire. It calculates request rate, error rate, latency percentiles, availability, SLO compliance, remaining error budget, and error-budget burn rate from that live in-memory window. Three consecutive windows above the 14.4× fast-burn threshold create an incident independently of the raw error-rate and latency thresholds. Repeated threshold violations create one active incident per service and trigger, allowing independent failures on the same service to remain visible, and capture that evaluation window, the last measured threshold-compliant window when one exists, and the currently observed downstream blast radius for later investigation. An operator can query live Jaeger traces for the suspected service from five minutes before detection through resolution or the current time.

Local-demo mutations can inject or restore bounded service faults and acknowledge or resolve incidents. Each mutation appends an immutable audit event; fault endpoints require the internal demo token and are inactive unless `DEMO_MODE=true`.

Incidents, their detection-time evidence and blast-radius snapshots, append-only audit events, orders, producer outbox state, and consumer receipts are stored in local PostgreSQL through versioned migrations. GraphQL reads the operational history, mutation audit writes finish before success is returned, and event processing recovers its producer and consumer state after restart. Telemetry samples, calculated service health, and observed topology remain in memory. See [history storage](history-storage.md) for local migration, inspection, and reset operations.

The control plane serves a web console on port 4000. Its topology, service metrics, incidents, fault actions, audit stream, recent distributed traces, aggregate PostgreSQL outbox state, and live RabbitMQ queue state use the same GraphQL API. Trace queries read bounded live results from Jaeger and expose identifiers, timing, parent relationships, operations, services, and error state without copying span tags or request content. Delivery queries expose only producer status counts, the oldest unsent timestamp, and ready, unacknowledged, and consumer counts for Nimbus's known queues; event payloads, identifiers, failure text, credentials, and arbitrary management endpoints remain internal. These backends are queried live and failures stay isolated from the rest of the dashboard rather than becoming persisted telemetry. Authenticated GraphQL subscriptions at `/graphql/ws` notify the console after health updates and successful incident/audit writes. The console refetches state on notifications and reconnection, retaining polling during connection or query failures. Bounded process-local queues keep slow subscribers from blocking telemetry ingestion; notifications do not replace durable history. See [live updates](subscriptions.md) for the protocol, authentication, and limits.

GraphQL requires a bearer identity on the backend. Viewers can read state, operators can generate traffic and manage incidents, and admins can inject or restore faults. The internal `/observe` ingestion route uses a separate bearer token shared only with workload services, so user credentials cannot submit telemetry and unauthenticated callers cannot fabricate operational state. Authenticated reports are also constrained to the known workload services and valid HTTP status and duration values before they can change topology or metric state. JSON request bodies are capped at 64 KiB before parsing; GraphQL requests are additionally limited by source address, query depth, query complexity, and query length. The documented `local-*` credentials exist only in Docker Compose demo mode.
